# 15. Least-privilege IAM, GitHub OIDC deploys, and secrets in SSM

- **Status:** Accepted
- **Date:** 2026-10-08

## Context
Two things need AWS permissions: the EC2 instance (pull images, read config and secrets, read docs, call Bedrock) and the GitHub deploy workflow (push images, upload a release, tell the instance to deploy). The usual shortcuts, long-lived access keys in GitHub secrets and broad managed policies, are the most common way cloud accounts get compromised.

## Decision
- **No long-lived AWS keys anywhere.**
  - The **instance** gets temporary credentials for its role from the instance metadata service (IMDSv2 only; hop limit 2 so containers can reach it).
  - **GitHub Actions** uses **OIDC**: each job gets a short-lived signed token from GitHub, and AWS STS exchanges it for temporary credentials for the deploy role.
- **The deploy role's trust policy is the security boundary.** `StringEquals` on `aud = sts.amazonaws.com` and `sub = repo:jasonlam11/cardflow:ref:refs/heads/main`. Pull requests, other branches, forks and other repositories cannot assume it. There's no `StringLike` wildcard.
- **Least privilege, resource by resource:**
  - Instance: pull from *our* 6 ECR repos; read SSM parameters under `/cardflow/*` only; read the artifacts bucket; `bedrock:InvokeModel` on the one Haiku 4.5 inference profile and its model; `AmazonSSMManagedInstanceCore` so SSM can run deploys.
  - Deploy role: push to our 6 repos; `s3:PutObject` under `deploy/*` only; `ssm:SendCommand` on *our* instance and the `AWS-RunShellScript` document only.
  - `Resource: "*"` appears only for actions AWS can't scope (`ecr:GetAuthorizationToken`, `ssm:GetCommandInvocation`). A test enforces this, and also that no action contains a wildcard.
- **Policies are written with `jsonencode`,** not the `aws_iam_policy_document` data source, so the offline tests can parse and assert on the exact JSON.
- **Secrets:** generated by Terraform (`random_password`, 32 alphanumeric characters), stored as **SecureString** in SSM Parameter Store (standard tier: free), and written to a root-only `.env` on the instance at deploy time. Nothing secret is committed, typed by a human, or passed through GitHub.

## Alternatives considered
- **Access keys in GitHub secrets:** simple, but the keys never expire, and if leaked they work from anywhere.
- **Secrets Manager:** automatic rotation, but $0.40 per secret per month; Parameter Store SecureString is free and enough without rotation.
- **`AdministratorAccess` / `PowerUserAccess` for the deploy role:** one compromised workflow would own the account.
- **SSH deploys (key in GitHub, port 22 open):** another long-lived secret and an open inbound port; SSM needs neither and logs every command.

## Consequences
- Generated secrets are stored in **Terraform state**, so the state bucket is private, encrypted, versioned and TLS-only (bootstrap stack). Anyone who can read state can read the secrets.
- Least privilege means adding a capability later (say, CloudWatch Logs) needs a policy change, which is the point.
- Rotation is manual: `terraform apply -replace='random_password.secret["ADMIN_API_KEY"]'`, then redeploy.
